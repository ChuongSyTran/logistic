I

What — Elasticsearch là cái gì?

Bản chất, hệ sinh thái, và mô hình dữ liệu — trước khi học cách dùng, cần biết đang cầm cái gì trong tay.

1.1 · Định nghĩa một câu

Elasticsearch là một search engine phân tán, lưu trữ document JSON, xây trên nền thư viện Apache Lucene, giao tiếp hoàn toàn qua HTTP/JSON.

VếNghĩa là gì
Search engineSinh ra để tìm kiếm & xếp hạng theo độ liên quan — không phải giữ dữ liệu chuẩn xác tuyệt đối
Phân tánDữ liệu tự chia nhỏ ra nhiều máy, tự nhân bản, tự cân bằng khi thêm/bớt máy
Document JSONĐơn vị dữ liệu là 1 object JSON, không phải 1 dòng bảng phẳng
Trên nền LuceneToàn bộ lõi tìm kiếm là của Lucene — ES là lớp phân tán + API bọc ngoài
HTTP/JSONKhông driver riêng, không ngôn ngữ query riêng kiểu SQL — chỉ là REST API

1.2 · Cây phả hệ — ai là ai

Hiểu điều này quan trọng: mỗi khi đọc về "inverted index", "segment", "BM25" — đó là Lucene. Còn "shard", "replica", "cluster", "index API" — đó là Elasticsearch.

❌ "ES thay được MySQL." Không có transaction đa document, không ROLLBACK. Dữ liệu tài chính luôn phải qua database thật trước.

❌ "Ghi xong tìm thấy ngay." Không — ES là Near Real-Time, mặc định trễ ~1 giây (chi tiết ở Phần III.5).

❌ "ES có JOIN như SQL." Gần như không — triết lý ES là denormalize: nhồi sẵn dữ liệu cần vào 1 document, chấp nhận trùng lặp để đổi lấy tốc độ.

II

Why — vì sao Elasticsearch tồn tại?

Bài toán mà B-Tree của SQL bó tay.

Bảng transactions 50 triệu dòng, tìm giao dịch có mô tả chứa "tiền cọc":

SELECT * FROM transactions WHERE description LIKE '%tiền cọc%' ORDER BY created_at DESC;
-- B-Tree sắp xếp trái→phải: tra được 'tiền%' (có điểm neo)
-- nhưng '%tiền%' không có điểm neo → quét cả 50 triệu dòng

Ví dụ dễ hiểu: B-Tree là danh bạ điện thoại — sắp theo tên nên tra "Nguyễn Văn A" cực nhanh. Nhưng hỏi "ai có chữ 'Văn' trong tên?" thì phải lật từng trang từ đầu.

2.1 · Lời giải: lật ngược chỉ mục

Thay vì hỏi "dòng này chứa từ nào?", ES lật ngược: "từ này nằm ở những dòng nào?"

Full scan (LIKE %x%)Inverted Index
Tra 1 từ khoáO(N) — N = tổng số dòngO(log T) — T = số từ khoá khác nhau
Khi dữ liệu tăng 100×Chậm tuyến tính theo NTừ vựng gần như không đổi → không chậm đi

Năm bài toán sau thì SQL gần như không có lời giải: xếp hạng theo độ liên quan, tìm trên nhiều cột có trọng số khác nhau, chịu lỗi chính tả, gom nhóm nhiều chiều tức thì, gợi ý gõ-tới-đâu-ra-tới-đó.

Dữ liệu tăng từ 1 triệu lên 100 triệu dòng, nhưng số từ tiếng Việt khác nhau gần như không đổi — inverted index vì vậy gần như không chậm đi theo quy mô dữ liệu.

3.2 · Analysis pipeline — nơi mọi thứ bắt đầu

Trước khi vào index, mọi văn bản bị băm nhỏ qua 3 chặng:

text vs keyword — cặp đôi gây nhầm lẫn nhất

🔑 term đi với keyword, match đi với text. Nhớ đúng 1 câu này là dùng được phần lớn ES.

Multi-field — 1 field, 2 cách đánh index

Field vừa muốn tìm mò vừa muốn lọc chính xác thì đánh index 2 lần:

"reference_id": { "type": "text", "fields": { "keyword": { "type": "keyword" } } }
// reference_id          → tìm full-text kiểu mò mẫm
// reference_id.keyword  → lọc chính xác / sort / gom nhóm

3.3 · Thuật toán chấm điểm — BM25

SQL trả lời "đúng/sai". ES trả lời "hợp lý tới mức nào" — qua 2 trực giác: TF (từ xuất hiện càng nhiều trong 1 document càng liên quan) và IDF (từ càng hiếm toàn index càng quý).

                                    f(q,D) · (k₁ + 1)
BM25(q,D) = IDF(q) · ─────────────────────────────────────────
                     f(q,D) + k₁ · (1 − b + b · |D| / avgdl)

k₁ = 1.2  → tốc độ bão hoà     b = 0.75 → mức phạt document dài

Với ứng dụng nghiệp vụ thông thường, gần như không bao giờ cần chỉnh k₁, b — chỉ đụng vào khi có bằng chứng cụ thể document dài đang bị thiệt thòi.

Block-Max WAND

Người dùng chỉ xem top-10. Mỗi lô postings lưu sẵn điểm trần — lô nào chắc chắn không lọt top thì bỏ qua nguyên lô, không tính điểm.

HNSW (ES 8.x)

Vector search / semantic search dùng đồ thị nhiều tầng, tìm láng giềng gần đúng ~O(log N). Xu hướng hiện nay: hybrid BM25 + kNN, gộp điểm bằng RRF.

Nhu cầuThuật toánGhi chú
Chịu lỗi chính tảLevenshtein Automatonfuzziness: AUTO, tối đa 2 ký tự sai
AutocompleteFST + edge n-gramCompletion Suggester
Đếm giá trị duy nhấtHyperLogLog++cardinality agg — xấp xỉ, sai số ~0.5%
Tính phân vị (p99)T-Digestpercentiles agg — xấp xỉ, chính xác ở đuôi

⚠️ cardinality và percentiles cố tình xấp xỉ để đổi lấy RAM cố định. Số liệu đối soát tài chính phải hỏi database, không hỏi ES.

3.4 · Segment — nền tảng của mọi hành vi "kỳ lạ"

Một shard không phải 1 file — mà là nhiều segment, và mỗi segment bất biến (immutable): ghi ra đĩa rồi không bao giờ sửa.

4 lợi ích

Không cần khoá khi đọc · cache vĩnh viễn hợp lệ · nén mạnh tay · OS page cache phát huy tối đa.

Cái giá phải trả

Xoá = đánh dấu tombstone (chưa xoá thật). Sửa = xoá + chèn mới. Dọn rác thật chỉ xảy ra khi merge.

3.6 · Kiến trúc phân tán

Vì sao master node luôn số lẻ (3, 5)?

Bầu master cần quá bán đồng ý. Với 2 node mà đứt mạng giữa chúng, mỗi bên tự nhận mình là master → split-brain, ghi dữ liệu khác nhau. Với 3 node, bên giữ được 2 mới thắng — bài học xương máu của ES thời kỳ đầu.

VI

How — triển khai thực tế

6.1 · Đồng bộ Database → Elasticsearch

Đây mới là chỗ hệ thống thật hay vỡ trận, không phải viết query.

① Dual Write

Ghi thẳng 2 nơi. Đơn giản nhưng không nguyên tử — ES fail là lệch vĩnh viễn. ← repo đang dùng

② Transactional Outbox

Ghi kèm 1 bảng outbox trong cùng transaction, worker đẩy sau. Không bao giờ mất sự kiện — chuẩn công nghiệp.

③ CDC (Debezium)

Đọc thẳng binlog MySQL. Code nghiệp vụ không cần biết ES tồn tại, nhưng hạ tầng nặng hơn.

Khuyến nghị thực tế: Outbox làm đường chính + Batch reindex chạy đêm làm lưới an toàn đối soát. Repo đã có sẵn Kafka — hạ tầng làm Outbox gần như có đủ.

6.2 · Query DSL — bộ khung cần thuộc

{ "query": { "bool": {
    "must":     [ ... ],   // AND — CÓ tính điểm
    "filter":   [ ... ],   // AND — KHÔNG tính điểm, ĐƯỢC CACHE
    "should":   [ ... ],   // OR — có tính điểm
    "must_not": [ ... ]    // NOT
}}}

🔑 Điều kiện chỉ trả lời đúng/sai (trạng thái, khoảng ngày, ID) → bỏ vào filter. Chỉ văn bản người dùng gõ mới cần must. Đúng chỗ có thể nhanh gấp nhiều lần nhờ cache bitmap.

6.3 · Implement trong wallet_service

File nguồn: wallet_service/internal/search/elasticsearch.go — toàn bộ phần ES của repo. Client: github.com/elastic/go-elasticsearch/v8.

Bài học error-handling của client ES

if err != nil    { ... }  // chỉ bắt lỗi TẦNG MẠNG (đứt cáp, sai host)

6.5 · Vận hành production — checklist

  1. Kích cỡ shard: 10–50GB mỗi shard — nhỏ quá phí quản lý, lớn quá phục hồi chậm
  2. JVM Heap: 50% RAM máy, không bao giờ vượt 31GB (mất compressed oops)
  3. Nửa RAM còn lại để dành cho OS page cache — đừng cấp hết cho heap
  4. Master node: số lẻ (3), tách riêng khỏi data node
  5. Snapshot định kỳ ra S3 — dù là read model, re-index toàn bộ vẫn tốn thời gian
VII–VIII

Ưu & nhược điểm

Ưu điểm
  • Tốc độ full-text phi thường trên trăm triệu document
  • Xếp hạng theo độ liên quan (BM25 + boost + rescore)
  • Mở rộng ngang thực thụ — thêm node tự cân bằng
  • Aggregation nhiều tầng trong mili-giây
  • API thuần HTTP/JSON — debug bằng curl
Nhược điểm
  • Không ACID, không transaction đa document
  • Mapping gần như không sửa được sau khi tạo
  • Ngốn RAM khủng khiếp (heap + page cache)
  • Deep pagination sập ở ngưỡng 10.000
  • Đồng bộ dữ liệu là bài toán riêng, dễ lệch

20 điều khắc cốt ghi tâm

Về bản chất
  • ES là read model — mất = re-index, không mất dữ liệu
  • ES = Lucene + phân tán + REST API
  • Không transaction đa document, không JOIN đúng nghĩa
Về mapping & analysis
  • term↔keyword, match↔text
  • Query phải qua cùng analyzer với lúc ghi
  • Mapping tạo rồi không sửa được — dùng alias từ đầu
Về nguyên lý bên trong
  • Segment bất biến — xoá = tombstone
  • Refresh 1s = Near Real-Time
  • Số primary shard không đổi được sau khi tạo
Về code
  • Check cả err lẫn res.IsError()
  • DocumentID = ID entity → idempotent
  • Không bao giờ gọi ES trong transaction database
